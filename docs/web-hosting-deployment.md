# 非公開Webアプリとしてのホスティング・認証方式

作成日: 2026-08-02／改訂: 2026-08-03（Cloudflare Pages + Access 最終仕様、受入試験チェックリスト追加）

## 現在の進捗段階（最重要・必ず最初に確認すること）

このドキュメントの内容には、コードとして実装済みの部分と、依頼者本人がCloudflareの管理画面で
行う必要がある部分が混在している。本人によるCloudflare側の設定・本番URLでの確認が完了するまで、
「公開済み」「認証済み」「利用可能」と断定しないこととし、以下の5段階で進捗を明示する。

| 段階           | 意味                                                                                                              | 現在の状態                 |
| -------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------- |
| ① 実装完了     | アプリ・CI/CD設定のコードがリポジトリに存在し、ローカルで検証済み                                                 | **完了**                   |
| ② 本人設定待ち | Cloudflareアカウント作成・APIトークン発行・GitHub Secrets登録・Accessポリシー設定など、本人のログインが必要な作業 | **未着手（本人作業待ち）** |
| ③ デプロイ完了 | GitHub Actionsが成功し、Cloudflare Pages上にアプリが実際に配信されている                                          | **未達（②が前提）**        |
| ④ 認証確認完了 | 本番URLで実際にCloudflare Accessのログイン画面が表示され、許可したメールアドレスでログインできることを確認        | **未達（③が前提）**        |
| ⑤ 受入完了     | 本ドキュメント末尾の受入試験チェックリスト全項目を本番環境で確認                                                  | **未達（④が前提）**        |

**結論: 実装済み・本人設定待ち。** 本人がCloudflare側の設定（下記「利用者が行う設定」）を
完了し、`main`ブランチへの反映後にGitHub Actionsが成功して初めて②→③→④→⑤へ進む。

## ホスティング・認証方式の比較

個人・単一利用者用途で「設定と保守が最も簡単」「無料枠または低コスト」「GitHub Actionsで
自動デプロイ可能」「GitHubリポジトリがprivateでも運用できる」という4条件を軸に比較した。

| 方式                                             | 認証の掛け方                                                                                                                                                                                                                 | 設定の手間                                                                     | 保守の手間                                                       | 費用                                                                                  | private repoでの可否                                                                      |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **Cloudflare Pages + Cloudflare Access（採用）** | エッジ（CDN層）でドメイン全体をゲート。認証方式はメールワンタイムPIN（追加のIDプロバイダ不要）                                                                                                                               | ダッシュボードで数クリック＋GitHub Secrets登録のみ。アプリ側のコード変更は不要 | Cloudflareが認証基盤自体を管理。証明書更新・セッション管理も自動 | Pages: 無料枠（ビルド500回/月、リクエスト無制限）。Access: 50ユーザーまで無料         | 可能（Actionsからビルド成果物をwranglerで直接push。Cloudflare側はリポジトリを参照しない） |
| Netlify + Netlify Identity                       | アプリ側にウィジェット（JS）を組み込み、ログインUIを自前で持つ必要がある                                                                                                                                                     | Identity設定＋フロントエンド実装が必要                                         | ライブラリ更新・トークン失効対応など継続的なコード保守が発生     | 無料枠あり（Identityは5ユーザーまで無料）だが、パスワード保護機能自体は有料プラン限定 | 可能                                                                                      |
| Vercel + Password Protection                     | Vercel標準のBasic認証的な保護機能                                                                                                                                                                                            | 設定は簡単                                                                     | 低い                                                             | **Proプラン（月額$20〜）が必須**。個人の低コスト要件に合わない                        | 可能                                                                                      |
| GitHub Pages（+ 自前認証）                       | GitHub Pagesは静的配信のみでサーバー側認証機構を持たない。クライアント側JSでの認証はビルド済みJS・問題データ自体を認証前にダウンロード可能にしてしまうため、要件（教材・問題データが認証なしで取得できないこと）を満たせない | -                                                                              | -                                                                | 無料                                                                                  | **除外**（要件を満たせないため不採用）                                                    |

**Cloudflare Pages（静的ホスティング）+ Cloudflare Zero Trust Access（認証）** を採用した。
理由は、(a) アプリのコードを一切変更せずにドメイン全体を認証で保護できる（＝「教材・問題
データが認証なしで取得できない」という要件を、アプリではなくインフラ層で確実に満たせる）、
(b) 追加のIDプロバイダ（Googleアカウント連携等）を用意しなくても、Cloudflareが自前で発行する
メールワンタイムPIN認証だけで完結する、(c) 無料枠のみで運用できる、(d) 独自ドメインの取得が
不要（`*.pages.dev`のサブドメインが無料でHTTPS付き提供される）、(e) GitHubリポジトリの
公開・非公開に関係なく、GitHub Actionsからビルド成果物を直接デプロイできる、という点で
他の選択肢より設定・保守の手間が明確に小さいため。

## Cloudflare Pages向け構成の確認結果（① 実装完了）

以下はいずれも既存のコードで既にCloudflare Pagesに適合していることを確認済みで、
変更は不要だった。

- **production buildの出力先**: `package.json`の`build`スクリプト（`tsc -b && vite build`）は
  Viteの既定通り`dist/`へ出力する（`vite.config.ts`で`build.outDir`は変更していない）。
- **Viteの`base`設定**: `vite.config.ts`に`base`指定はなく既定値`/`のまま。ルーティングも
  `src/main.tsx`で`<BrowserRouter>`を`basename`指定なしで使用しており、`index.html`の
  アセット参照（`/assets/...`, `/icon-192.png`等）もすべてルート相対パス。Cloudflare Pagesは
  `<project>.pages.dev`のルート直下に配信するため、追加の`base`設定は不要と確認した。
- **SPAの直接URLアクセス・再読み込み対応**: `public/_redirects`に`/* /index.html 200`を配置済み。
  `npm run build`実行時に`dist/_redirects`へ自動コピーされることを確認済み（Cloudflare Pagesは
  ビルド出力に`_redirects`ファイルがあれば自動的にSPAフォールバックへ適用する）。
- **PWAのmanifest・Service Worker・静的アセット**: `dist/index.html`に
  `<link rel="manifest" href="/manifest.webmanifest">`と`registerSW.js`の読み込みタグが
  ビルド時に自動挿入され、`dist/manifest.webmanifest`・`dist/sw.js`・`dist/workbox-*.js`・
  アイコン（`icon-192.png`, `icon-512.png`）がすべて`dist/`直下に生成されることをビルド結果で
  確認済み。パスはすべてルート相対のため、Cloudflare Pagesのルート配信と整合する。

これらの確認のため、`src/`・`vite.config.ts`・`index.html`・ルーティング設定への変更は
一切行っていない（要件通り、必要のない変更はしていない）。

## 実装内容（① 実装完了・このリポジトリに含まれるコード）

- `public/_redirects`: `/* /index.html 200`（SPAフォールバック）。
- `.github/workflows/deploy.yml`: `main`ブランチへのpush、または手動実行
  （`workflow_dispatch`）をトリガーに、以下の順序で実行する。1つでも失敗した場合、
  それ以降のステップ（デプロイを含む）は実行されない。
  1. `actions/checkout` → ソース取得
  2. `actions/setup-node`（Node 22）→ `npm ci`（依存関係の導入）
  3. `npm run lint`（自動品質検査: ESLint）
  4. `npm run format:check`（自動品質検査: Prettier整形チェック）
  5. `npm run typecheck`（自動品質検査: TypeScript型検査）
  6. `npm run test`（単体テスト: Vitest）
  7. `npm run validate:questions`（設問・教材データの検証）
  8. `npm run build`（production build、`dist/`を生成）
  9. `npx playwright install --with-deps chromium`（Playwrightの導入）
  10. `npm run test:e2e`（E2Eテスト、`vite preview`起動→Playwright 15件）
  11. `cloudflare/wrangler-action@v3`で`dist/`をCloudflare Pagesへデプロイ
      （1〜10がすべて成功した場合のみ実行される）
  - 既存の`.github/workflows/ci.yml`（push/pull_request全般に対するCIチェック、全ブランチ対象）は
    そのまま維持し、デプロイ専用の`deploy.yml`（`main`ブランチ限定）と役割を分離している。
- 既存アプリのコード（`src/`、`vite.config.ts`、PWA設定、IndexedDBアクセス層）は無変更。
- オフライン動作をこのセッションのLinux環境上で`vite preview`起動→Playwrightで初回アクセス
  （Service Worker登録完了を待機）→ネットワークをoffline化→再読み込み・`/drill`への画面遷移、
  という手順で検証し、初回アクセス後は完全にオフラインでも動作することを確認済み
  （この検証はホスティング・認証方式に依存しないアプリ側のPWA機構のみの検証であり、
  Cloudflare Pages上・Cloudflare Access通過後の実地確認は、下記「本番受入試験」を本人が
  行うことで完了する）。

## GitHub Secrets（② 本人設定待ち）

`deploy.yml`は以下3つのGitHub Secretsを参照する。このリポジトリの
**Settings → Secrets and variables → Actions → New repository secret** から、本人が登録する。

| Secret名                  | 値の内容                                           | 取得場所                                             |
| ------------------------- | -------------------------------------------------- | ---------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`    | Pages編集権限を持つAPIトークン                     | Cloudflareダッシュボード → プロフィール → API Tokens |
| `CLOUDFLARE_ACCOUNT_ID`   | CloudflareアカウントID                             | Cloudflareダッシュボードの右サイドバー               |
| `CLOUDFLARE_PROJECT_NAME` | Cloudflare Pagesのプロジェクト名（例: `g-kentei`） | 手順2で作成したPagesプロジェクト名と一致させる       |

この3つのSecretsが未登録の間は、`deploy.yml`のデプロイステップ（11番目）が認証エラーで
失敗する。1〜10（品質検査・E2E）はSecrets登録前でも独立して実行・成功しうる。

## 利用者が行う設定（② 本人設定待ち・ダッシュボード操作が必要なため代行不可）

Cloudflareアカウントの作成・APIトークン発行・Access（Zero Trust）のポリシー設定は、
本人のログイン・アカウント情報が必要なため、このセッションから代行できない。以下の手順を
一度だけ実施すれば、以後は`main`ブランチへのpushで自動デプロイされる。

1. **Cloudflareアカウント作成**（無料）: https://dash.cloudflare.com/sign-up を開き、メール
   アドレスとパスワードを登録する（クレジットカード登録は不要）。
2. **Pagesプロジェクトの作成**: ログイン後のダッシュボード左メニューから
   「Workers & Pages」→「Create」→「Pages」タブ→「Upload assets」を選び、プロジェクト名
   （例: `g-kentei`）を入力して作成する。この画面ではファイルのアップロードを求められるが、
   何かダミーファイル1つをアップロードして作成を完了させればよい（実際のデプロイ内容は
   後でGitHub Actionsが上書きする）。プロジェクト名は上記GitHub Secretsの
   `CLOUDFLARE_PROJECT_NAME`と必ず一致させる。
3. **APIトークンの発行**: ダッシュボード右上のアイコン→「My Profile」→「API Tokens」タブ→
   「Create Token」→テンプレート一覧から「Edit Cloudflare Workers」を選ぶ（Pages編集権限を
   含む）→対象アカウントを選択して「Continue to summary」→「Create Token」。表示された
   トークン文字列をコピーする（この画面を閉じると再表示できないため、必ずこの時点でコピーする）。
4. **GitHub Secretsへの登録**: このリポジトリの「Settings」タブ→左メニュー「Secrets and
   variables」→「Actions」→「New repository secret」で、上記表の3つを1つずつ登録する。
5. **Cloudflare Zero Trust（Access）の設定**（認証の本体、下記「Cloudflare Access設定手順」を参照）。
6. 設定完了後、`main`ブランチへのpush（またはGitHubの「Actions」タブから
   `Deploy (Cloudflare Pages)`ワークフローを「Run workflow」で手動実行）でデプロイが始まる。

## Cloudflare Access設定手順（画面の順序に沿った初心者向け手順）

**必須条件（すべて満たすこと）**: 対象ホストは本番の`pages.dev`ドメイン／Pathはドメイン全体
（特定の画面だけに絞らない）／許可するメールアドレスは本人の1件のみ／認証方式はメールの
ワンタイムPIN／未認証の状態ではトップページだけでなく、HTML・JavaScript・CSS・JSON・
教材データ・設問データ・`manifest.webmanifest`・`sw.js`（Service Worker）にも一切到達できない
こと。

1. https://one.dash.cloudflare.com/ を開く。
2. 初回アクセス時は「Zero Trustプランの選択」画面が出るので、**「Free」プラン**を選ぶ
   （チーム名の入力を求められた場合は任意の名前でよい、例: `gkentei`）。
3. 左メニューから「Access」→「Applications」を開く。
4. 「Add an application」ボタンをクリックし、「Self-hosted」を選ぶ。
5. 「Application domain」の設定画面で、以下を入力する。
   - Application name: 任意（例: `G検定学習ドリル`）
   - Session Duration: **推奨値: 24時間**。単一利用者・非公開運用のため長め（例: 1週間〜1ヶ月）
     に設定してもセキュリティ上のリスクは限定的だが、初期設定では短めの24時間を推奨し、
     実際の利用頻度に応じて後から緩めることを推奨する（複数PCを使う場合、PCごとに個別に
     セッションが切れるため、頻繁な再ログインが煩わしい場合は延長を検討する）。
   - **Domain**: 手順2で作成したPagesプロジェクトのドメイン（例: `g-kentei.pages.dev`）を
     入力する。
   - **Path欄は空欄のままにする**（これが必須条件の「ドメイン全体」に対応する。ここに
     `/admin`のような特定パスを入力すると、そのパス以外＝JSバンドルや設問データを含む
     すべての静的アセットが認証なしで到達可能になってしまうため、絶対に特定パスへ絞らないこと）。
   - 「Next」をクリックする。
6. 「Add policies」画面で以下を設定する。
   - Policy name: 任意（例: `本人のみ許可`）
   - Action: 「Allow」
   - Session duration: 手順5と同じ値（自動で引き継がれる場合はそのままでよい）
   - Configure rules → Include → 条件の種類で「Emails」を選び、依頼者本人の1つの
     メールアドレスのみを入力する（他のメールアドレス・ドメイン全体許可・
     「Everyone」などは選ばない）。
   - 「Next」→「Add application」で確定する。
7. 「Authentication」タブ（またはZero Trust全体の「Settings」→「Authentication」）で、
   「Login methods」に**「One-time PIN」が有効になっていること**を確認する（Cloudflare
   Accessでは既定で有効になっているため、通常は追加設定不要）。他のログイン方法
   （GitHub連携等）を追加する必要はない。
8. 設定完了後、シークレットウィンドウ（プライベートブラウジング）で対象ドメイン
   （例: `https://g-kentei.pages.dev/`）を開き、Cloudflare Accessのログイン画面
   （メールアドレス入力欄）が、アプリの画面より先に表示されることを確認する。
   これが表示されれば、ドメイン全体が保護されている（下記「本番受入試験」の該当項目に対応）。

## 本番受入試験チェックリスト（⑤ 受入完了の判定基準）

デプロイ完了（③）・認証確認完了（④）の後、本人が本番URLに対して以下をすべて確認できた
時点で「⑤ 受入完了」とする。

### 認証

- [ ] シークレットウィンドウで本番URLを開くと、アプリの画面より先にCloudflare Accessの
      認証画面（メールアドレス入力欄）が表示される
- [ ] 許可したメールアドレスでワンタイムPINをメール受信でき、そのPINでログインできる
- [ ] 許可していないメールアドレスを入力した場合、ログインできない（アクセス拒否される）
- [ ] 未認証の状態で、アプリ画面（トップページ）以外の静的ファイルの直接URL
      （例: `/manifest.webmanifest`、`/sw.js`、`/assets/`配下のJSファイルのURLを直接開く）に
      アクセスしても、認証画面にリダイレクトされる（＝迂回してデータへ到達できない）

### アプリ機能

- [ ] トップ画面（ダッシュボード）が正常に表示される
- [ ] ホーム／教材／ドリル／復習／模擬試験／弱点分析／設定の全画面へナビゲーションから
      移動できる
- [ ] いずれかの画面でブラウザの再読み込み（F5）をしても、404にならず正常に表示される
      （`_redirects`によるSPAフォールバックの確認）
- [ ] 章別ドリルで問題に回答し、結果画面まで到達できる
- [ ] 復習（SRS対象・誤答・ブックマーク）画面が動作する
- [ ] 模擬試験を最後まで解いて結果画面を確認できる
- [ ] 10章すべての教材・設問データが欠落なく表示される（章一覧・問題数が期待通り）
- [ ] 画面のどこにも文字化け（日本語の文字化け）や白画面が発生しない

### 保存

- [ ] ドリル・模擬試験の回答後、進捗・履歴・ブックマークが保存される（ダッシュボードの
      集計に反映される）
- [ ] ブラウザを完全に閉じて再度開いても、保存した内容が残っている
- [ ] 設定画面のエクスポートでJSONファイルを出力できる
- [ ] 出力したJSONファイルをインポートすると、データが復元される
- [ ] 別のPCで同じ本番URLを開いても、学習履歴が自動的には同期されないこと
      （＝IndexedDBが端末ごとに独立していることの確認。これは不具合ではなく仕様である）

### PWA・オフライン

- [ ] ブラウザ（Chrome/Edge）のアドレスバーまたはメニューから「アプリをインストール」
      （PWAとしてPCに追加）できる
- [ ] 一度オンラインで画面を開いた後、ネットワークを切断した状態でインストール済みPWAを
      起動できる
- [ ] オフライン状態のまま、ホーム／ドリル／復習等の主要画面へ画面遷移できる
- [ ] オフライン状態でドリルに回答して保存し、その後ネットワークを再接続しても、
      オフライン中に保存した内容がそのまま残っている（データが消えない）

## 費用と制約

- **想定月額費用**: 0円。Cloudflare Pages（無料枠: ビルド500回/月、帯域・リクエスト数は
  実質無制限）、Cloudflare Access（無料枠: 50ユーザーまで、今回は1ユーザーのみ使用）、
  GitHub Actions（privateリポジトリでも無料枠は月2,000分、本ワークフローは1回あたり
  数分程度）。いずれも無料枠の範囲内で収まる想定。
- **無料枠の範囲**: 上記の通り。利用者が増えても50名まではCloudflare Access側は無料枠内。
  Cloudflare Pagesのビルド回数上限（500回/月）は、`main`への1日十数回程度のpushでも
  通常は超えない想定。
- **利用者数の前提**: 現時点で1名（依頼者本人のメールアドレスのみ）。将来的に利用者を
  増やす場合は、Cloudflare Accessのポリシーに許可するメールアドレスを追加するだけでよく、
  アプリ側のコード変更は不要。
- **IndexedDBは端末ごとに独立する**: 学習履歴・SRS状態・模擬試験履歴・ブックマークは
  すべてブラウザのIndexedDBにのみ保存される、既存のクライアントサイド完結型の設計を
  維持しているため、複数のWindows PCからそれぞれ同じURLへアクセスしても、各PC・各ブラウザの
  IndexedDBは完全に独立しており、自動的なデータ同期は一切行われない。
- **認証とデータ同期は別機能である**: Cloudflare Accessは「誰がアプリに到達できるか」を
  制御するものであり、「複数端末間でデータを同じ状態に保つ」機能ではない。両者は独立した
  仕組みであり、Accessを設定しても端末間の学習データは自動的には揃わない。
- **ブラウザのキャッシュ・データ削除で履歴が消える可能性**: IndexedDBはブラウザの
  サイトデータ・閲覧履歴の削除操作（「Cookieとサイトデータを削除」等）で消去されうる。
  重要な学習履歴は、設定画面のエクスポート機能で定期的にJSONファイルとして
  バックアップすることを推奨する。
- **将来、自動同期を追加する場合に必要となる構成**（今回は未実装・参考情報）: 複数端末間で
  学習履歴を自動的に同期するには、現在のクライアントサイド完結型の設計を拡張し、
  (a) 何らかのバックエンド（例: Cloudflare Workers + D1/KVなどのデータストア、または
  Firebase等のマネージドサービス）を追加してIndexedDBの内容をサーバー側にも保存する仕組み、
  (b) 端末をまたいで同一人物であることを識別する認証（現在のCloudflare Accessは「アプリへの
  到達可否」の認証であり、アプリ内でユーザーを識別する仕組みではないため、別途アプリ内
  認証か、Access発行するユーザー情報ヘッダーをアプリ側で読み取る実装が必要)、
  (c) 端末間の同時編集時のデータ競合解決（コンフリクト解決）ロジック、が必要になる。
  これは既存のオフラインファースト設計からの大きな変更となるため、今回は意図的に
  範囲外とした。

## バージョン管理

このWebアプリ化対応は、既存のRelease Candidate 1（タグ`v1.0.0-rc1`、コミット`1f7919e`）や
Windowsデスクトップ版（コミット`828c942`）とは区別されるコミットとして記録する。
既存の正式版・RCタグは変更していない。`main`ブランチへの反映は、本ドキュメント上部の
品質検査（`npm run ci`・`npm run test:e2e`）がすべて成功したことを確認した後に行う。

## 既知の制約（アプリアーキテクチャ上のもの、再掲）

- **複数端末間でのデータ同期はできない**（上記「費用と制約」を参照）。
- **Cloudflare Access通過後の同一オリジン内の認可はアプリ側では行っていない**: 認証は
  「Cloudflareのエッジで、登録した1つのメールアドレス以外は一切コンテンツに到達できない」
  という形で担保しており、アプリ自体（React側）はログイン状態を意識しない。将来的に
  利用者を複数名に増やす場合も、Access側のAllowリストにメールアドレスを追加するだけで
  アプリ側の変更は不要な設計だが、その場合は各利用者のIndexedDBが完全に分離される
  （データ共有はされない）点に注意。
- 本ドキュメントに記載の手順（Cloudflareアカウント作成・APIトークン発行・Accessポリシー
  設定）は、認証情報の性質上このセッションから実施できず、依頼者本人による1回限りの
  手動設定が必要。それ以外（アプリコード・CI/CD設定一式）は実装・検証済み。
