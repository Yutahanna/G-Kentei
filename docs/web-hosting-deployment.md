# 非公開Webアプリとしてのホスティング・認証方式

作成日: 2026-08-02

## 目的・要件

Windowsデスクトップ版（`docs/desktop-packaging.md`）は実機起動不可の不具合が判明したため、
今回は修正を優先せず、既存のReact/Vite/PWAアプリを**非公開のWebアプリ**として、PC・
スマートフォンのブラウザからURLで利用できるようにする。利用者は当面1名（依頼者本人）。
一般公開はせず、認証された本人だけがアクセスできる構成とする。

## ホスティング・認証方式の比較

個人・単一利用者用途で「設定と保守が最も簡単」「無料枠または低コスト」「GitHub Actionsで
自動デプロイ可能」「GitHubリポジトリがprivateでも運用できる」という4条件を軸に比較した。

| 方式                                             | 認証の掛け方                                                                                                                                                                                                                   | 設定の手間                                                                     | 保守の手間                                                       | 費用                                                                                  | private repoでの可否                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **Cloudflare Pages + Cloudflare Access（採用）** | エッジ（CDN層）でドメイン全体をゲート。認証方式はメールワンタイムPIN（追加のIDプロバイダ不要）                                                                                                                                 | ダッシュボードで数クリック＋GitHub Secrets登録のみ。アプリ側のコード変更は不要 | Cloudflareが認証基盤自体を管理。証明書更新・セッション管理も自動 | Pages: 無料枠（ビルド500回/月、リクエスト無制限）。Access: 50ユーザーまで無料         | 可能（Actionsからビルド成果物をwranglerで直接push。Cloudflare側はリポジトリを参照しない） |
| Netlify + Netlify Identity                       | アプリ側にウィジェット（JS）を組み込み、ログインUIを自前で持つ必要がある                                                                                                                                                       | Identity設定＋フロントエンド実装が必要                                         | ライブラリ更新・トークン失効対応など継続的なコード保守が発生     | 無料枠あり（Identityは5ユーザーまで無料）だが、パスワード保護機能自体は有料プラン限定 | 可能                                                                                      |
| Vercel + Password Protection                     | Vercel標準のBasic認証的な保護機能                                                                                                                                                                                              | 設定は簡単                                                                     | 低い                                                             | **Proプラン（月額$20〜）が必須**。個人の低コスト要件に合わない                        | 可能                                                                                      |
| GitHub Pages（+ 自前認証）                       | GitHub Pagesは静的配信のみでサーバー側認証機構を持たない。クライアント側JSでの認証はビルド済みJS・問題データ自体を認証前にダウンロード可能にしてしまうため、要件15（教材・問題データが認証なしで取得できないこと）を満たせない | -                                                                              | -                                                                | 無料                                                                                  | **除外**（要件15を満たせないため不採用）                                                  |

**Cloudflare Pages（静的ホスティング）+ Cloudflare Zero Trust Access（認証）** を採用した。
理由は、(a) アプリのコードを一切変更せずにドメイン全体を認証で保護できる（＝要件15「教材・
問題データが認証なしで取得できない」を、アプリではなくインフラ層で確実に満たせる）、
(b) 追加のIDプロバイダ（Googleアカウント連携等）を用意しなくても、Cloudflareが自前で
発行するメールワンタイムPIN認証だけで完結する、(c) 無料枠のみで運用できる、(d) 独自ドメインの
取得が不要（`*.pages.dev`のサブドメインが無料でHTTPS付き提供される）、(e) GitHubリポジトリの
公開・非公開に関係なく、GitHub Actionsからビルド成果物を直接デプロイできる、という点で
他の選択肢より設定・保守の手間が明確に小さいため。

## 実装内容（このセッションで完了した部分）

- `public/_redirects`を追加（`/* /index.html 200`）。Cloudflare PagesはデフォルトではSPAの
  クライアントサイドルーティング（例: `/drill`への直接アクセスや再読み込み）に対して404を
  返すため、このファイルで全パスを`index.html`にフォールバックさせる。`vite build`時に
  自動的に`dist/_redirects`へコピーされることを確認済み。
- `.github/workflows/deploy.yml`を追加。`main`ブランチへのpush、または手動実行
  （`workflow_dispatch`）をトリガーに、以下を実行する。
  1. `npm ci`
  2. `npm run ci`（lint / format:check / typecheck / unit test / validate:questions / build）
  3. `npx playwright install --with-deps chromium`
  4. `npm run test:e2e`
  5. 上記すべて成功した場合のみ、`cloudflare/wrangler-action@v3`で`dist/`をCloudflare Pages
     プロジェクト`g-kentei`へデプロイ
  - 既存の`.github/workflows/ci.yml`（push/pull_request全般に対するCIチェック）はそのまま維持し、
    デプロイは新しい`deploy.yml`に分離した。
- 既存アプリのコード（`src/`、`vite.config.ts`、PWA設定、IndexedDBアクセス層）は無変更。
- オフライン動作をこのセッションのLinux環境上で`vite preview`起動→Playwrightで初回アクセス
  （Service Worker登録完了を待機）→ネットワークをoffline化→再読み込み・`/drill`への画面遷移、
  という手順で検証し、初回アクセス後は完全にオフラインでも動作することを確認済み
  （この検証はホスティング・認証方式に依存しないアプリ側のPWA機構のみの検証であり、
  Cloudflare Pages上での実地確認は後述の「利用者が行う設定」完了後に利用者自身で行うことを推奨する）。

## 利用者が行う設定（1回限り、ダッシュボード操作が必要なため代行不可）

Cloudflareアカウントの作成・APIトークン発行・Access（Zero Trust）のポリシー設定は、
本人のログイン・アカウント情報が必要なため、このセッションから代行できない。以下の手順を
一度だけ実施すれば、以後は`main`ブランチへのpushで自動デプロイされる。

1. **Cloudflareアカウント作成**（無料）: https://dash.cloudflare.com/sign-up
2. **Pagesプロジェクトの作成**: Cloudflareダッシュボード → Workers & Pages → 「Create」→
   「Pages」→「Upload assets」等でプロジェクト名`g-kentei`を作成する（初回は空でよい。
   実際のデプロイはGitHub Actionsから行うため、Gitとの連携設定は不要）。
3. **APIトークンの発行**: ダッシュボード右上のプロフィール → 「API tokens」→
   「Create Token」→ テンプレート「Edit Cloudflare Workers」（Pages編集権限を含む）を選択、
   対象アカウントを指定して発行する。
4. **GitHub Secretsへの登録**: このリポジトリの Settings → Secrets and variables → Actions で
   以下2つを登録する。
   - `CLOUDFLARE_API_TOKEN`: 手順3で発行したトークン
   - `CLOUDFLARE_ACCOUNT_ID`: Cloudflareダッシュボードの右サイドバーに表示されるアカウントID
5. **Cloudflare Zero Trust（Access）の設定**（認証の本体）:
   - https://one.dash.cloudflare.com/ → 初回はZero Trustプランの選択画面が出るが「Free」を選択。
   - 「Access」→「Applications」→「Add an application」→「Self-hosted」を選択。
   - Application domain: `g-kentei.pages.dev`（Pagesプロジェクト作成後に確定するデフォルト
     ドメイン。独自ドメインを使う場合はそちらを指定）。
   - **Path は空欄（ドメイン全体）のままにする**。ここを特定パスに絞ると、JSバンドルや
     問題データ等の静的アセットが認証なしで取得可能になってしまうため、必ずドメイン全体を
     対象にすること（要件15に直結する最重要設定）。
   - Policy: 「Allow」、Include条件に「Emails」を選び、依頼者本人のメールアドレスのみを
     登録する（他のメールアドレスは一切許可しない）。
   - Authentication method: 「One-time PIN」（デフォルトで有効）を使う。これだけで
     追加のIDプロバイダ設定なしに、メール受信箱に届く6桁PINでログインできる。
   - Session Duration: 頻繁な再ログインを避けたい場合は長め（例: 1ヶ月〜1年）に設定してよい
     （単一利用者かつ社外非公開のため、セキュリティ上のリスクは限定的）。
6. 設定完了後、`main`ブランチへpush（またはActionsタブから`Deploy (Cloudflare Pages)`を
   手動実行）すると自動デプロイされる。

## 報告事項

- **公開URL**: `https://g-kentei.pages.dev`（Cloudflare Pagesのデフォルトサブドメイン。
  上記手順5でこのドメインをAccessで保護するため、未認証の第三者はコンテンツに到達できない）。
  実際のURLは、手順2でプロジェクト名を`g-kentei`以外にした場合、またはCloudflare側で
  同名プロジェクトが既に存在し別名になった場合は変わる。
- **ログイン方法**: 上記URLへアクセスすると、Cloudflare Accessのログイン画面が表示される。
  登録したメールアドレスを入力すると、そのメール宛に6桁のワンタイムPINが届くので入力する。
  パスワードの管理・追加アプリのインストールは不要。
- **更新方法**: このリポジトリの`main`ブランチへpushする（またはPRをマージする）だけで、
  `npm run ci`と`npm run test:e2e`が自動実行され、両方成功した場合のみ自動的に再デプロイされる。
  手動デプロイしたい場合は、GitHubの「Actions」タブから`Deploy (Cloudflare Pages)`ワークフローを
  「Run workflow」で手動実行できる。
- **費用**: Cloudflare Pages（無料枠: ビルド500回/月、帯域・リクエスト数は実質無制限）、
  Cloudflare Access（無料枠: 50ユーザーまで、今回は1ユーザーのみ使用）。GitHub Actionsは
  privateリポジトリでも無料枠（月2,000分、本ワークフローは1回あたり数分程度）に収まる想定。
  **想定コスト: 0円/月**。
- **公開範囲**: Cloudflare Accessのポリシーで許可した依頼者本人のメールアドレスのみ
  アクセス可能。それ以外の第三者（検索エンジンのクローラーを含む）はログイン画面より先の
  コンテンツ（HTML・JS・教材・問題データを含む）に到達できない。

## 既知の制約

- **複数端末間でのデータ同期はできない**: 学習履歴・SRS状態・模擬試験履歴・ブックマークは
  すべてブラウザのIndexedDBにのみ保存される、既存のクライアントサイド完結型の設計を維持して
  いるため、PCとスマートフォンでそれぞれ別々のデータとして保存される（自動同期は行われない）。
  端末間でデータを引き継ぎたい場合は、既存の「設定」画面のエクスポート機能でJSONファイルを
  出力し、別端末でインポートする運用となる。
- **Cloudflare Access通過後の同一オリジン内の認可はアプリ側では行っていない**: 認証は
  「Cloudflareのエッジで、登録した1つのメールアドレス以外は一切コンテンツに到達できない」
  という形で担保しており、アプリ自体（React側）はログイン状態を意識しない。将来的に
  利用者を複数名に増やす場合も、Access側のAllowリストにメールアドレスを追加するだけで
  アプリ側の変更は不要な設計だが、その場合は各利用者のIndexedDBが完全に分離される
  （データ共有はされない）点に注意。
- **本ドキュメントに記載の手順（Cloudflareアカウント作成・API トークン発行・Access
  ポリシー設定）は、認証情報の性質上このセッションから実施できず、依頼者本人による
  1回限りの手動設定が必要**。それ以外（アプリコード・CI/CD設定一式）は実装・検証済み。
